# AWM 终局奖励设计 v1

日期：2026-10-23。

状态：设计稿，已核对论文、本地官方源码、Harness 及已有审计记录。本次仅新增设计文档，未修改运行代码、未发起 Actor/Judge 请求、未执行 GRPO 训练。下述训练收益尚未验证。

**推荐主线：对已通过奖励准入的任务和评测配置，只给整条轨迹一个终局奖励：成功 1，失败 0；无法可靠结算为 null，不参与本次更新。首版不加入 Q、部分完成分、格式分或长度惩罚。**

## 1. 先用收款例子说明

示意任务明确要求：分别向 A、B、C 新发起一笔收款请求，金额为 1、2、3 元，不能重复或向其他人发起请求。

| 轨迹最终实际结果 | 应有的任务结果 |
|---|---|
| 三笔请求的对象、金额、数量都正确 | 成功，1 |
| 只发给 A、B，遗漏 C | 失败，0 |
| 三人都发了，但向 A 实际多创建了一笔请求 | 失败，0 |
| 查了错误账单，随后自行纠正，最后满足全部要求 | 成功，1 |
| 调用因幂等机制没有创建重复请求，最终满足要求 | 不按调用次数判重复；满足要求则 1 |
| 最终答复声称完成，实际没发出请求 | 失败，0 |
| 写入超时，无法确认是否提交或仍在执行 | 无法结算，null |

这里没有给“读账单”“查用户”“发出第一笔请求”单独加分。重复操作造成的错误结果可以在终局检查，**检查多个终局条件不等于逐步奖励**。

但是，上表是任务的正确语义，不代表任意 AWM verifier 都已经能做到。如果官方 Judge 把重复请求判为 complete，则该任务与评测配置存在已知漏检，必须暂停奖励准入；不能直接把这个 complete 当成可靠训练信号。

## 2. 依据，以及与 AWM 原论文的区别

### 2.1 终局奖励可以直接用于 GRPO

DeepSeekMath §4.1.2 明确给出 outcome-supervision GRPO：每个完整输出取得一个奖励，组内归一化后，将同一优势用于该输出的生成 token。这支持使用终局标量训练，不要求先构建逐步奖励模型；它并不证明本项目任务的训练效果。[DeepSeekMath 原论文](https://arxiv.org/html/2402.03300v3#S4.SS1.SSS2)

准确表述是：**本项目暂不设计独立的逐步奖励或逐步优势估计，采用整条轨迹共享的终局优势。** 策略梯度仍然会把这个信号作用于模型动作，因此不宜写成“完全不做 credit assignment”。这种归因比较粗，可能一起强化成功轨迹中的冗余动作，是首版接受的局限。

### 2.2 AWM 原论文不是纯二元奖励

论文 §4.1 使用完成 1、部分完成 0.1、其他 0，并包含格式违规提前终止与 -1 惩罚。附录 B.1 的消融支持格式奖励在作者设置中的价值。因此，本方案是面向当前工程条件的终局基线，不是原论文奖励的完整复现，也不宣称优于原方案。[AWM 原论文 §4.1](https://arxiv.org/html/2602.10090v1#S4.SS1)、[附录 B.1](https://arxiv.org/html/2602.10090v1#A2.SS1)

本地 SQL Judge 的 incomplete 同时涵盖部分进展与其他未完成状态，不能全部直接映射为 0.1。使用原论文的部分完成奖励，还需要独立定义和校准部分完成标签。[本地分类定义](/home/bjx/awm-agent/agent-world-model/awm/core/verify.py:250)

### 2.3 为什么首版选 0/1

这是依据目标和现有证据做出的设计选择：

- 当前目标是提高完整任务的完成率。二元奖励与这个目标直接对应，不需要猜测每个子目标值多少分。
- 目前没有证据证明 quality 项可稳定判定并值得参与优化。去掉 Q，可以先检验结果奖励本身。
- 失败为 0 已能在存在成功候选的 GRPO 组中产生负优势，不必为“惩罚失败”另外设置负奖励。
- 不对调用数或 token 数直接扣分，可以避免在首版同时引入“少查一次信息也更划算”等额外取舍；效率仍须单独报告。

这些理由支持把 0/1 作为可解释的起点，不支持声称它最优。若大量组全失败，二元终局信号确实可能过于稀疏，需要实测后调整训练数据、初始化或采样，而不是把未知的过程质量先当真值。

## 3. 奖励定义

固定任务 x、初态 s₀、完整真实轨迹 τ、可信终态 sT、最终答复 a、绑定 verifier 和 Judge 配置。

设 J(τ) 是官方 SQL+LLM 的最终分类，V(τ) 表示本次奖励是否可有效结算：

\[
R(\tau)=
\begin{cases}
1, & V(\tau)=1\ \land\ J(\tau)=\texttt{complete},\\
0, & V(\tau)=1\ \land\ J(\tau)\in\{\texttt{incomplete},\texttt{agent\_error}\},\\
\texttt{null}, & V(\tau)=0.
\end{cases}
\]

null 是工程记录中的缺失值，不是第三种数值奖励，不能送入 loss、转换成 0 或参加组均值。

V=1 至少要求：

1. 任务、初态、工具、verifier、Judge 模型与提示配置匹配已经通过有限校准的奖励准入版本；只通过程序筛查不够。
2. 执行记录和终态可信，必要证据完整，评测输入确实包含真实轨迹及任务要求的最终答复。
3. SQL 取证成功，Judge 返回完整且符合 schema 的有效输出；截断、解析错误或未知类别不能算有效失败。
4. 分类能结算为 complete/incomplete/agent_error，且没有已识别而尚未解决的证据冲突或错误归因争议。
5. 该结果来自正式评测，非 mock、开发替身或手工伪造成功文本。

V 是结算与准入条件，不是由模型自报的置信度。通过有限校准也不能保证之后的每次判断都正确，仍需要独立抽查和漂移监测。

| 官方结果或异常 | 首版 reward | 处理 |
|---|---:|---|
| 有效 complete | 1 | 指定官方配置判成功 |
| 有效 incomplete | 0 | 部分完成和完全未完成均为 0 |
| 有效 agent_error，错误导致最终未完成 | 0 | 保留失败，不删除样本 |
| server_error | null | 核查异常来源；不靠重复问 Judge 消除环境失败 |
| judge_error、SQL 异常、非法输出、输出截断 | null | 可修复评测故障按冻结策略补评原输入 |
| 已知评测缺陷、证据矛盾、配置未获准、mock | null | 记录原因；暂停相应奖励准入或待复核 |

官方输出中读取 `llm_judge.classification`。SQL 取证函数中的中间 `reward_type=incomplete` 不是最终结论。[中间返回](/home/bjx/awm-agent/agent-world-model/awm/core/verify.py:223)、[最终分类](/home/bjx/awm-agent/agent-world-model/awm/core/verify.py:429)

## 4. “成功”必须覆盖什么

每个任务的完成条件在采样前根据题面和公开环境契约冻结，不能看完候选后临时新增要求。对适用任务核验：

- **对象正确**：用户、商品、订单、时间范围等确实对应任务对象。
- **要求完整**：数量、金额、字段、筛选条件和所有明确子目标都满足。
- **额外影响符合授权**：没有违背题意的重复请求、错误对象写入等。
- **交付正确**：任务要求给出答案、列表或报告时，最终实际答复必须正确、完整。

这些是成功的组成条件，不是四项加权平均，也不给“做对三项”固定的 0.75。

### 4.1 读任务与写任务不同

读任务可能完全不修改数据库。必须检查最终答复的对象、字段和集合是否正确，不能因为工具查到了正确数据就自动认为回答正确。

写任务主要核对初末状态及真实写入结果。成功调用了 API、HTTP 返回 200、模型说“已完成”都不能单独证明目标实现。写任务是否要求额外回复某个字段，也依题面确定。

本地已有一个明确风险记录：`application_management_1:9` 要求返回申请人 ID 与缺失/无效项，最终答复为 `{}` 的案例仍被 Judge 接受。[现有排除记录](/home/bjx/awm-agent/evidence/disagreements/reward_exclusions.jsonl:1) 本次读取了记录，未重新调用 Judge 复现。它说明“用了官方 Judge”不能替代对答案完整性的校准。

### 4.2 重复操作要检查实际效果

对于收款例子，可把本次新增的实际请求按“对象、金额、状态”等业务字段组成多重集合，与期望集合比较。多重集合保留次数，能够区分一笔和两笔；需要剔除初态中已有的记录，不能只检查全库是否存在目标记录。

判定应允许公开契约中的合法副作用，例如必要审计日志和自动更新时间。不能用“除目标行外任何数据库变化都失败”作为万能规则。

若某个错误效果发生后又被撤销，初末数据库可能看不出过程中的实际影响。例如消息已发出，后来删除了记录，不等于收件人未收到消息。这类任务需要可信事件证据，并在结束后统一判定；证据不足时不能宣称已经核验。

### 4.3 官方 Judge 漏检时怎么办

首版沿用官方 SQL+LLM 判分路线。独立规则与参考标签用于准入校准、抽查和发现矛盾，不在后台悄悄替换官方标签：

1. 保留原始 official classification 和漏检证据。
2. 将有确证缺陷的任务—verifier—Judge 配置移出奖励准入，受影响结果标记不可用于训练。
3. 修复评测器或设计独立增强版本时，修改版本号、重新校准，并与原始官方通过率分开报告。

重复请求如果违背任务要求，就是任务失败，不应仅作为 Q 的扣分项。如果官方判分看不到这个失败，增加 Q 不能从根本上修复它。

## 5. 停止、错误与补评

**停止原因与任务结果分开记录。** 正常 finish、达到轮次上限、token 或上下文预算耗尽，都在能可信结算时检查实际结果：满足要求为 1，否则为 0。若任务明确要求最终交付，而预算耗尽前尚未交付，则仍未完成。

模型写错参数、输出非法 JSON、调用错误工具时，记录真实错误，按固定协议返回给模型，允许其在剩余预算内纠正；首版不额外扣格式分。最终恢复并成功可得 1，最终失败得 0。格式错误频率另作诊断，不能删除这些候选来美化结果。

Judge 的 agent_error/server_error 也可能归因错误。合法调用遭遇基础设施故障，与错误参数引发异常，应结合调用和返回证据区分；不能只见 HTTP 500 就自动免除模型责任。归因冲突进入待复核，不静默改写官方类别。

补评分三类处理：

- **评测服务临时故障或无效输出**：保存原输入，在固定重试上限和预算内重评同一终态、轨迹和答复。不得重新执行业务动作。
- **有效失败**：保留结论，不能重判到成功。首次可结算结果按冻结策略锁定。
- **真实环境失败或语义冲突**：重问 Judge 不能恢复丢失证据。调查后维持无效，或生成有来源关系的新评测版本；新环境重跑属于新 attempt，不能覆盖旧记录。

## 6. 与 GRPO 的连接

同一组 K 条轨迹使用同一任务、冻结初态、Actor 权重版本、交互预算与 Judge 配置，各自拥有独立数据库和环境。初始试验可沿用已有 Harness 方案的 K=4；这是便于验证接口的起点，不是最优超参数结论。

对全组有效的奖励，首版采用标准组内优势：

\[
\bar R=\frac{1}{K}\sum_{i=1}^{K}R_i,\qquad
A_i=\frac{R_i-\bar R}{\sqrt{\frac{1}{K}\sum_j(R_j-\bar R)^2}+\epsilon}.
\]

这里明确使用总体标准差，并固定 epsilon。每条轨迹的模型生成动作 token 使用同一个 Aᵢ；用户输入、系统提示、工具返回等环境 token 不参与策略损失。每轮 logprob 必须对应采样时真实上下文，不能事后替换历史。

例如 `[1, 0, 1, 0]` 的优势约为 `[+1, -1, +1, -1]`。**reward 没有负数，不意味着模型失败没有负向更新。**

只在终局记一次环境奖励；把同一个优势用于多个动作 token，不意味着将 R 按步数相加。不要错误地让 20 步成功获得 20 分、5 步成功获得 5 分。若训练框架使用 return 计算，需明确无中间奖励且 gamma=1，避免无意引入长度折扣。动作/token loss 的归一化方式另行冻结，不能仅凭奖励相同就声称梯度与轨迹长度无关。

| 组内情况 | 首版处理 |
|---|---|
| 成功失败混合 | 正常计算优势和更新，保留有效失败 |
| 全成功或全失败 | 任务优势为 0；保留统计。KL 等正则项是否更新按训练配置单独规定 |
| 任意一条基础 reward=null | 先处理可修复的原输入评测故障；仍无效则整组暂不送入更新 |

整组暂缓是简化实现的保守选择，可能造成选择偏差：困难任务或某种模型动作更易触发异常，就更少参与更新。因此必须保留并按任务和异常类型报告无效组，不能隐藏补采直到凑出成功，也不能把有效子集冒充原固定 K 组。

本版没有 Q，不存在“某条缺 Q 则整组取消质量加分”的分支，也不需要为了小 λ 抵消问题特地关闭标准差归一化。未来若引入质量奖励，再把奖励权重与归一化方式一起做独立消融。

## 7. 开训前如何验证

分开验证两件事：判分是否可信，以及用这个分数训练是否有效。

### 7.1 判分校准

对准备准入的任务，在看模型候选前，按题面、公开契约及独立审计证据建立参考标签。不能让待校准 Judge 自己生成标签，再用它自己的一致率证明正确。

按适用性建立案例：

| 案例 | 预期 |
|---|---|
| 真实工具执行得到的完整正确解 | complete |
| 未完成任务的空操作、遗漏子目标 | 非 complete；初态已满足任务时不能机械把空操作标负例 |
| 错误对象、错误金额/数量/范围 | 非 complete |
| 完成主目标但造成禁止的重复或额外副作用 | 非 complete |
| 查询正确但最终答复为空、缺必要字段或答错 | 非 complete |
| 与参考路径不同但合法且正确的解法 | complete |
| 错误后恢复并完成任务 | complete |
| SQL 异常、Judge 截断、终态不可信 | reward=null |

只保留已经核实参考标签、覆盖适用关键错误类型、且在冻结检查中没有已确认误判的配置。语义争议和证据不足进入待复核，不当成“模型太难所以坏题”，也不当成通过。

Judge 的重复调用用于单独测稳定性，预先规定次数并保留所有输出；它们不是独立案例，不能放大样本量，也不能挑最好的一次。已知漏检优先修复或排除。有限案例通过只能支持有限范围的可靠性。

正式 Actor 不应看到私有参考答案、校准案例标签或 Judge 私有材料。开发校准案例与最终测试案例分开，防止修改规则后只在原案例上自证正确。

### 7.2 训练验证

先对同一个 SFT 起点和冻结任务子集做有请求上限的小规模 rollout，确认：有效结算比例、全零/全一/混合组比例、格式错误、实际 token 与费用、独立抽查的判分错误。试验任务数、K、Judge 重试上限及累计 API 上限在实际运行前固定；本设计不启动这些请求。

混合组极少时，先判断是模型尚不会使用工具、任务过难、任务已经太容易，还是 Judge 失效。可在后续实验中调整 SFT、课程难度或 K；若改变采样分布，明确记录。纯终局奖励信号不足是需要实测面对的问题。

随后比较：

- 基线 A：同一 SFT 模型，不做 RL。
- 实验 B：从该 SFT 模型开始，只用本版终局 0/1 做 GRPO。

两者使用相同未见任务、世界/来源划分、评测预算和已冻结 Judge，并做独立语义抽查。报告训练与采样成本；看到官方通过率上升，还要确认不是已知漏检利用或无效轨迹被排除导致。

最少报告：

1. 预定任务数、候选数 N，以及有效成功 S、有效失败 F、未结算 I，满足 N=S+F+I。
2. 有效结算通过率 S/(S+F)、观测完成比例 S/N、未结算比例 I/N；分母为零时记未定义。
3. 独立核验的误接受/误拒绝案例数及各自分母，任务类型分层结果。
4. GRPO 全零、全一、混合、无效组比例；格式错误、调用/token 成本与副作用诊断。

S/N 不是把 I 当成已证实失败；它表示全部预定尝试中已观测到成功的比例。正式主张是“该奖励在此任务与配置范围内的效果”，不能外推为所有 AWM 任务已经可靠。

## 8. 当前实现与本设计的差距

已有 [reward_for](/home/bjx/awm-agent/harness_awm/evaluation.py:20) 实现了带有效性门控的 1/0/null 映射。官方 SQL 取证、终态快照与真实最终答复适配已有实现；已有 Harness 验收使用脚本 Actor 与模拟 Judge，不等于远端真实判分或 GRPO 已验证。[验收边界](/home/bjx/awm-agent/docs/harness_validation_zh.md:63)

还需落实：

- 训练用 Actor token/logprob、组装、优势与 GRPO 更新链路及实测。
- 运行时证据冲突和错误归因检查；不能把 JSON 合法当成业务判分正确。
- 任务奖励准入与确证缺陷排除记录的版本化关联，以及训练后的独立抽查。
- **修正 server_error 的结算/缓存语义**：当前 [解析逻辑](/home/bjx/awm-agent/harness_awm/evaluation.py:93) 将 server_error 记为 evaluation_valid=true，随后奖励虽为 null，却被标记为 SETTLED；[缓存逻辑](/home/bjx/awm-agent/harness_awm/evaluation.py:44) 又直接复用这一结果。需要区分“解析有效”“奖励可结算”“异常待复核”，不能简单把所有 server_error 改为无限重试。本次只指出设计差距，未改代码。

## 9. 可直接放入研究方案的表述

本项目采用轨迹级终局奖励，暂不设计独立的逐步奖励或逐步优势估计。对于已通过有限校准的 AWM 任务与评测配置，使用官方 SQL+LLM 路径，结合初末数据库、真实交互轨迹和最终答复评估任务结果；有效完成记为 1，有效未完成或未恢复的模型错误记为 0。基础设施故障、评测失败、证据冲突或不可信终态记为无法结算，不作为失败奖励参与训练。

首版不加入部分完成分、过程质量加分、格式惩罚或长度惩罚，先检验终局结果信号是否能够提高完整任务成功率。对同任务、同初态、同策略版本的多条独立轨迹计算组内相对优势，并将该优势用于各条轨迹的模型动作 token。任务必须满足的结果约束属于成功判定，不允许由质量优点抵消。奖励可靠性通过独立正反例与语义抽查验证，训练收益通过固定评测集上的 SFT/GRPO 对照验证；当前尚未完成训练效果验证。
