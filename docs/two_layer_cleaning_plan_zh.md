# AWM 两层数据清洗方案：环境有效性与答案／官方 Judge 可靠性

日期：2026-10-23。状态：设计稿；本次未执行新清洗或模型请求。

## 1. 目标和边界

产出在指定数据版本、环境版本和官方 Judge 配置下，通过两层检查的任务子集，并保留排除依据和未完成事项。

- 第一层：环境、数据库、工具实现是否正确支持任务。
- 第二层：题目的参考答案／预期结果是否正确，官方 SQL+LLM Judge 是否能区分已核实的正确与错误结果。
- 不设计轨迹质量评价、rubric、Agent harness、SFT 或 RL 数据生产流程；测试操作只用于形成可核查的输入和结果。
- 正式判分仅使用官方 `sql` 模式，不以自写判分器或 `pure_code` 替代。独立查询、计算及核查条件用于给测试案例定标签，不能替代官方最终判分。
- `keep` 表示通过本方案规定的有限测试，不表示证明任意答案、任意操作下 Judge 都正确。
- 过滤单位为 `(task_id, data_hash, environment_hash, verifier_hash, judge_config_hash)`。排除当前组合，不删除原始任务。

## 2. 当前证据与旧流程的问题

本地 `docs/cleaning_approach_zh.md`、旧清洗记录表明：此前大量暂存来自逐题检查未实现，而非已经发现题目或 Judge 有缺陷。`evidence/disagreements/review_zh.md` 同时记录了官方误放、旧规则漏条件、时间及范围解释不一致等不同情况。

`cleaning_runs/all_v1/report_zh.md` 记录过结构／初始化筛查，但明确没有完成全量运行时工具业务检查和语义认证。本方案不把其 `retain` 直接升级为 `keep`，也不把历史报告数值当作本次重新验证结果。

新方案解决工程欠账的方式：逐题配置取代逐题完整插件；程序枚举覆盖义务；缺项进入有预算的补全队列；已知缺陷才排除。不能靠降低准入条件或更换“暂存”的名字提高完成率。

## 3. 冻结输入与官方接口

每次运行保存题目清单及顺序、原始七类资产及哈希、源码版本、依赖版本、数据库初态哈希、工具契约、verifier 绑定、运行时间／时区、Judge 模型标识及请求参数、协议版本。不保存密钥。

官方参考：`agent-world-model/awm/core/verify.py` 中 `run_verifier`、`run_llm_judge` 和 `verify`。当前代码的 SQL 路径读取初末数据库，向 LLM 传入题目、`trajectory` 中的记录及 SQL 执行结果；模型通过配置指定，代码中请求参数为 `temperature=1.0`、`max_completion_tokens=4096`。这些属于当前源码事实，后续以冻结版本为准。

“继续使用官方 Judge”指保留原始 verifier、提示词、输入构造及判定流程，同时固定实际使用的模型与参数；使用官方代码不自动等于复现官方论文的模型配置。

测试适配只记录真实工具调用／返回、最终答复和数据库快照，按官方格式送入。不得编造工具返回，不附加私有正确标签、独立核查条件或参考答案给被测 Judge。正确答案本身作为被测试答复当然可以出现。

必须检查最终答复是否确实进入官方 LLM 输入：仅写入顶层 `messages` 不保证 SQL 路径会把它送入，须核对原生记录格式与最终请求。适配器漏传是清洗实现错误；官方原生路径确实无法观察题目要求的答案，是官方输入链路的问题。二者不能混淆，也不能偷偷修改官方提示词后仍称原配置通过。

相对时间题固定并记录环境和 verifier 实际使用的参考时间。优先使用原生支持的时钟设置；若无法在不改变语义的条件下复现，标记时间依赖及复核需求，不擅自选一个能让答案通过的日期。

## 4. 第一层：环境、数据库和工具

| 检查项 | 做法 | 通过证据／错误归因 |
|---|---|---|
| 原始资产与绑定 | 检查缺失、重复冲突、题面一致性、任务与环境／verifier 映射 | 唯一可追溯绑定；冲突不可随意选一份 |
| 初始化 | 使用官方初始化语义完整建立数据库；失败在另一份全新实例复现 | 原始 SQL、错误、数据库快照；区分发布数据错误与本机依赖错误 |
| 数据库结构和一致性 | 表、字段、实际约束、外键及完整性检查；题目关键数据可定位 | 不自行增加数据集没有声明的业务约束；空表或查无对象并非天然错误 |
| 工具接口 | 启动服务，枚举工具，核对输入输出与公开契约 | 不能只用 Python 编译成功代替运行检查 |
| 读取业务行为 | 对任务相关对象、过滤、排序、分页、聚合做数据库独立核对 | 工具返回与正确范围的数据库事实一致 |
| 写入业务行为 | 在独立数据库执行合法新增、修改、删除，比较返回及实际变更 | 目标对象、字段和声明的副作用一致；按工具契约检查失败调用是否产生不当写入 |
| 重置与隔离 | 两次从同一冻结初态执行关键探针，核对语义结果 | 不把自增 ID 或时间戳字节相同当成普遍要求；不同案例不能相互污染 |

环境级初始化和同一工具实现的基础测试可以缓存复用，缓存键包含代码、契约、初态、时间设置和探针版本。业务参数分支仍需按任务补测；一个参数样例成功不证明该工具所有分支正确。

先建立“任务—依赖工具—数据对象”表。全局初始化／重置缺陷阻断整个当前环境实例；局部工具缺陷只传播到确认依赖它的任务。依赖范围尚未明确的任务进入补查，不武断排除整个环境，也不放行可能受影响的任务。

合法替代工具确实能完成同一任务时，应验证替代路径，再决定该题是否被局部缺陷阻断。探针自身参数错、超时、缺依赖分别记录，不能直接记作环境硬缺陷。

第一层发布口径为“任务依赖范围通过”。若环境中仍有未测工具，不宣称整个环境全部工具已通过。

## 5. 第二层 A：从题面建立最小核查条件

这里的条件只表达答案／结果正确性，例如对象、数值、过滤范围、时间、输出字段；没有过程质量维度或评分等级。

采用固定结构，Codex 填写数据而非为每题从零编写完整插件：

```json
{
  "requirement_id": "r_price",
  "source_quote": "set the price of product A to 80",
  "kind": "field_equals",
  "target": "product A",
  "field": "price",
  "expected": 80,
  "evidence_source": "final_db",
  "probe_template": "update_field",
  "negative_template": "wrong_value"
}
```

模板先覆盖常见查询、筛选／聚合、新增、字段修改、删除、关联操作、批量操作和时间条件。复杂题由模板组合；模板不支持的条件登记为能力缺口，不能默默忽略，也不能把题目强行改成模板支持的意思。

每题按以下顺序构造：

1. **第一次提取**：仅依据题面、公开工具契约和必要的数据结构提取要求，不参考官方 Judge 结论，不抄官方 verifier 条件。
2. **独立复提取**：另一轮核查先直接读完整题面，独立列条件，再与第一份比对；重点检查每个动作、并列子句、限定词、数量、否定词、时间、输出要求。可以顺序执行，不要求部署多 Agent 系统。
3. **双向覆盖**：每条条件必须有原文／契约依据；每个要求性子句必须映射到条件，或有可复核的“背景说明／歧义”解释。词句定位及空缺由程序检查，语义是否漏掉仍需核查。
4. **执行取证**：每条条件绑定对象解析、真实查询／计算和可解释结果。数值聚合保留参与计算的记录，不能只存一个总数。
5. **冻结版本**：正反例测试前冻结条件和标签。发现遗漏允许修正，但新版本必须使相关标签、案例和 Judge 结果失效并重新检查，不能为了符合某次 Judge 输出改标签。

两轮模型同意不等于独立真值。关键条件必须落到题面依据与数据事实；不同查询若复用同一个错误过滤范围，也不能算独立核验。

对于已有参考答案，先隐藏它完成独立复算，再比较。没有显式答案时，构造已核实的参考结果，并审查官方取证／判定依据；不能假定 `gen_verifier.jsonl` 是正确答案库。当前读取的 `gen_tasks.jsonl` 样本是任务文本列表，`gen_verifier.jsonl` 样本包含代码和生成记录，因此实施时必须逐项识别实际资产，不虚构独立答案字段。

含糊的“最近”“所有客户”“返回结果”等，如果题面和公开契约不足以确定范围、时点或输出位置，应列为语义复核；不能自行增加 restaurant_id、唯一数量、固定措辞或固定工具顺序。

## 6. 第二层 B：由覆盖义务自动产生正反例

程序先产生待完成的案例矩阵，再生成案例。不能由 Codex 自由决定“写几个例子应该够了”。

每道题至少包含一个真实可达且满足全部条件的正例；每个适用的独立条件至少有一个能实际违反它的负例。额外按题型枚举高风险边界及等价正确表达。最小集合是每题动态导出的覆盖要求，不是统一规定“一个正例加三个负例”。

| 题型／条件 | 正例义务 | 负例及边界义务 |
|---|---|---|
| 对象定位 | 正确对象的正确结果 | 错对象；如实际无法构造，记录原因并复核 |
| 修改／新增／删除 | 满足全部明确结果条件，真实工具执行成功 | 错值、漏字段／漏操作；未执行时仅当初态不满足目标才算负例 |
| 多要求／批量 | 全部对象和子要求满足 | 逐项遗漏、对象集合缺失／多出；仅题意规定范围时适用 |
| 筛选／聚合 | 正确过滤及独立复算；合理等价格式 | 漏过滤、错误数值、错误成员、漏所要求字段；需确认改变后结果确实不同 |
| 时间／范围 | 按明确参照时点和包含关系得到正确结果 | 起止边界、时区和周期偏移；无明确依据时不强定标签 |
| 明确输出要求 | 正确结果确实出现在题目要求的输出位置 | 错答案、漏必要内容、空答案；不能把每道 Fetch 题都自动套用“必须最终文本返回” |
| 不唯一的合法答案 | 至少覆盖可构造的代表性合法替代 | 不把合法工具路径、措辞、排列差异当成负例；有排序要求的题例外 |

重复写入、额外副作用只有在违反明确要求或工具契约时才成为正式负例。否则属于诊断挑战或语义待定，不计入已知负例分母。

每个正式案例执行后重新计算全部条件：正例必须全部满足；负例必须至少有一项明确违反，尽量只破坏目标条件。若条件存在依赖、无法单独破坏，记录实际违反的条件集合及原因，不能伪称单条件覆盖。

每条覆盖义务只允许以下结果：`covered`、`not_applicable_with_evidence`、`missing`。仅生成文件、把数值改了却未改变答案、空调用仍已满足目标、违反了与目标无关的条件，都不算有效覆盖。`not_applicable` 不能只是模型写一句“不适用”；需给出初态、契约或不可分离条件的证据并复核。

正例和负例优先通过真实工具形成初末状态；案例操作参数来源应为题面、公开常量或前序工具返回。直接改数据库可用于诊断 verifier 对某状态是否敏感，但在证明状态可通过合法工具达到之前，不凭该案例认定生产使用下的误判。审计查询可以读数据库，但不得把未通过工具获得的隐藏 ID 冒充合法输入来源。

工具原始记录必须和初末状态一致；只读题的答案变体可共享同一次冻结读取证据，清楚标注哪个最终答复是测试变体。官方所需记录只承担输入事实，不用于过程质量评价。

## 7. 第二层 C：先核实标签，再调用官方 Judge

测试链路：独立条件核查 → 案例标签与证据冻结 → 执行原版 SQL 取证 → 保存实际送入官方 LLM 的输入 → 获取官方判定 → 比较标签。

独立取证检查未完成时停止派发，回到补全队列。官方 SQL 若缺必要事实，不补造官方输出：检查官方输入中的其他真实证据是否可覆盖；若整个官方输入无法区分一个正例和一个负例，记录可复现的信息缺口。SQL 运行异常和 LLM 语义误判分开统计。

沿用原严格验收原则：每个冻结正式案例预先安排 **5 个 Judge slot**，全部有效且与独立标签一致才满足该案例的通过条件。不以多数票通过，不为了通过不断重采样。5 次通过只能说明这 5 次测试，不能推导总体误判概率上界或完全可靠。

- 对正确案例，预期为 `complete`。
- 对正常执行但结果错误的案例，预期为有效的 `incomplete` 或与实际错误相符的 `agent_error`；若研究目标还要求细分类正确，则另记分类一致性，不与二元成功判定混淆。
- `server_error`、`judge_error`、输出截断、非法格式属于无效／异常，不能当成成功识别负例。
- 保存每次原始响应、finish reason、解析状态、请求用量和槽位。只加外层记录，不改官方判分内容。
- 传输失败按预先固定策略有限重试，并计入物理请求量；已返回的有效错误判定不能被后续正确判定覆盖。截断不能通过加大输出上限后继续冒充原配置同一测试。
- 一旦出现语义不一致，立即复核独立标签、数据状态、官方实际输入和绑定。确认案例正确且输入链路无适配错误后，即足以将当前配置任务移出可用集；其他重复结果仅补充稳定性证据，不推翻已确认错误。
- 可在确认缺陷后提前停止其余付费 slot，记录 `not_run_due_to_confirmed_defect`；被排除任务不必继续花钱集齐通过证书。

## 8. 防止再次卡在“规则没写全、例子没补齐”

每题维护一份 coverage 表，至少包含：原文子句、条件 ID、取证完成度、正例 ID、负例覆盖、适用边界、预期标签、实际状态、官方输入哈希、5 个 Judge slot、待补项。

自动补全采用有界队列：

| 缺口 | 下一步自动工作 | 仍未解决时的归类 |
|---|---|---|
| 原文子句未映射 | 重新提取遗漏条件并核查来源 | 语义明确但生成失败：工程待办；题意不明确：复核 |
| 模板不支持 | 归入同类能力缺口，优先扩展一次共享模板 | 工程待办，不给每题重复生成大型插件 |
| 取证查询失败 | 根据真实 schema／工具返回修正查询 | 清洗实现错误；证明资产缺陷后才排除 |
| 正例不满足要求 | 修复测试配方，重放并检查全部条件 | 未证明可达；不把构造器失败当题目不可解 |
| 负例实际仍正确 | 重新实例化能真正破坏条件的变体 | 覆盖缺口，不能记为 Judge 误放 |
| 案例缺失 | 根据矩阵自动实例化对应模板 | 工程待办，并保留失败原因及累计成本 |
| 已核实案例与 Judge 冲突 | 复核标签、官方取证和输入 | 确认缺陷则排除，语义争议则复核 |

建议初始设置每题每阶段最多 2 轮自动修补；这是工程预算参数，不是正确性门槛，可根据试点调整。达到上限时保留具体欠账，转交按模板／原因聚类的工程队列；不能无限重试，也不能改成通过。

共享模板修复后，只重跑依赖它的任务，同时使旧覆盖、标签和 Judge 结果按依赖关系失效。候选生成阶段可迭代；正式评价案例一经查看 Judge 结果后，其修订属于新版本，不能挑选最有利案例。

防止共同漏检：每个新模板至少对首个完整实例做原文逐句核查；已完成任务另抽取冻结的分层随机样本，绕开已生成的条件表重新读题。可自动解决的明显缺口自动处理，真实语义争议及抽查发现的问题再集中人工复核，不要求每题人工签字。若发现共享模板系统性漏项，撤回受影响的通过状态并补测整个受影响集合。

## 9. 状态与准入

每题保留两层独立状态，同时有一个总状态：

| 总状态 | 含义 | 是否进入可用集 |
|---|---|---|
| `keep` | 第一层依赖范围通过；第二层条件、标签、案例覆盖及官方 Judge 测试通过 | 是，附版本和测试范围 |
| `reject` | 有确证的环境／工具／答案／官方判分链路缺陷，记录根因与影响范围 | 否 |
| `pending_build` | 规则提取、查询、模板、案例或接口适配未完成 | 否，必须有具体下一步 |
| `blocked_run` | 依赖、网络、预算、无效模型输出等执行阻断 | 否，单列可重跑条件 |
| `review` | 题意、标签、时钟、范围等仍有真实语义争议 | 否，明确争议点 |

多个问题保留独立原因，不用一个状态覆盖全部证据。基础数据已确认有错但可修复的任务仍从当前版本移出；修复副本使用新版本重走相关检查。当前主交付是清洗，不自动改官方 Judge。

`keep` 的机械门槛：所有适用检查均有已验证证据；没有 `missing` 覆盖；所有正式案例标签已核实；官方绑定和输入正确；全部必需 slot 有效且判定正确；无未解决的适用缺陷。即使所有机械门槛通过，也保留语义遗漏的抽查风险说明。

## 10. 完整示例

示例题：把商品 A 的价格改为 80 元，库存改为 20。假设冻结初态为 A 的价格 100、库存 10，另有可定位的商品 B；工具允许分别设置这两个字段。

先检查数据库、查找商品工具和修改工具，并独立确认其读写对应正确对象。随后提取三个结果条件：对象 A、价格 80、库存 20。

| 案例 | 实际状态／结果 | 独立标签与依据 |
|---|---|---|
| P1 | A 的价格 80、库存 20 | 正确，全部要求满足 |
| N1 | 只把 B 改为 80／20，A 不变 | 错误，目标对象要求未满足 |
| N2 | A 的价格 81、库存 20 | 错误，价格条件违反 |
| N3 | A 的价格 80、库存仍为 10 | 错误，库存条件违反 |
| N4 | A 完全未变，却答复已完成 | 错误，数据库目标状态未满足 |

N1 同时影响 A 的多个状态条件，应记录真实违反集合，不能声称它只违反一个条件。N4 的适用性依赖已冻结初态；初态已经满足目标时不能沿用负例标签。

如果生成器漏掉“库存”，原文覆盖复核应发现它；如果 N3 未生成，案例矩阵阻止进入 Judge 验收；如果 N3 实际库存已是 20，标签核查阻止把它算负例；只有 N3 确实错误而官方 Judge 接受，才构成误放证据。

本例为 5 个正式案例，全部完成需 25 次 Judge 请求；条件生成、修补及复核模型调用另计。该数字仅解释预算，不能当作所有题的固定案例数。

## 11. 执行顺序、预算和交付

1. **协议与接口检查**：冻结清单和 Judge 配置，验证真实记录能完整进入官方输入；复核旧争议分类，保留原证据。
2. **第一层增量完成**：复用哈希和设置匹配的初始化证据，补运行时工具与业务探针；逐题建立依赖范围。
3. **模板打通**：从原 100 题中选取各已有题型的代表，完成从提取到 Judge 测试的闭环。代表题只验证实现，不能代表其他题自动通过。
4. **完成原 100 题试点账目**：复用原清单与顺序；已确认阻断任务保留根因，其余逐题完成覆盖或给出具体工程／语义／运行阻断。旧案例需重验标签和输入，不能直接继承为金标准。
5. **按试点调整工程和预算**：报告未完成原因的数量／比例、每题请求和 token 的分布、模板复用、人工复核量。若仍主要卡在工程未实现，先补模板，不扩大付费量。
6. **全量执行与发布**：只有累计请求／token 上限得到明确授权后，按题型批次展开；通过项分层抽查，系统性遗漏使受影响集合退回。输出 keep-only 清单和对应证据。

在运行前冻结每批任务数、生成／修补／标签复核／Judge 各阶段上限、传输重试上限和总累计上限；到限断点保存，不默认为继续。设各题正式案例数为 C_i，严格 Judge 预算基础为 `5 × Σ C_i`，再单列构造、复核、无效请求及传输重试。排除后提前停止可节约预算，但必须如实记录未执行部分。不凭历史单题成本外推可靠总价。

核心统计同时报告任务级和案例级：两层覆盖任务数、各状态任务数、工程缺口减少量、经核实正例／负例数、全部测试通过任务数、误接受／有效负例判定次数、误拒绝／有效正例判定次数、无效请求数及分母。5 次调用有相关性，不能当成 5 个独立案例；另外报告“至少一次误判的案例／任务”比例。抽查样本与刻意挑选的争议样本分开统计。

建议产物：`manifest.json`、`environment_checks.jsonl`、`tool_checks.jsonl`、`task_dependencies.jsonl`、`requirements.jsonl`、`coverage.jsonl`、`cases.jsonl`、逐案例初末数据库及真实调用记录、`judge_results.jsonl`、`build_queue.jsonl`、`review_queue.jsonl`、`tasks.keep.jsonl`、`tasks.reject.jsonl`、`tasks.pending.jsonl`、`cost_report.json`、`report_zh.md`。所有派生产物带版本／哈希与依赖来源；续跑按证据键去重，不重复花费或复用已失效结论。

本方案的验收目标是完成有证据的两层清洗，并显著减少可修复的工程欠账；不预设 keep 比例，不承诺消灭所有待核查题目，也不将通过清洗等同于训练系统已经就绪。
