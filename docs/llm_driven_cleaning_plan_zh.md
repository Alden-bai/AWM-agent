# AWM 逐题 LLM 清洗方案：预期结果、真实正反例与官方 Judge 验证

日期：2026-10-24。状态：**待实施设计稿，未运行**。

本次只新增本文档；未启动环境、清洗、模型请求或训练。下面的模块、接口和配置是拟议设计，不代表已有实现。本方案不自动替换历史协议，不修改原始数据和已有清洗结论。

## 1. 目标与基本思路

按照用户提出的流程：

> 一道原始题目 → LLM 分析应该满足的结果 → LLM 通过真实工具完成候选正例 → 程序读取真实状态 → 核实案例标签 → 构造并执行反例 → 冻结案例 → 官方 SQL+LLM Judge 判分 → 程序比较标签与判分 → 发布有限测试通过的任务子集。

这里“正确答案”包括数据库状态条件、查询结果和题目明确要求的最终答复，不是所有题都对应一个完整的目标数据库。

关键约束：

1. **LLM 提出的答案先是候选。**模型判断与官方 Judge 一致，只说明一致，不能独立证明正确。
2. **执行是实际执行。**LLM 选择工具和参数，程序执行 MCP 调用并记录真实返回，不让模型模拟数据库或编造工具结果。
3. **按实际结果贴标签。**一个“打算做错”的案例，实际可能仍正确；一个“打算做对”的案例，也可能没有完成任务。
4. **正式判分仍只使用官方 `sql` 路径。**独立 SQL/Python 检查用于审计和确定案例标签，不替代官方判分，不使用 `pure_code` 作为准入依据。
5. **保留全部明确要求。**控制成本靠复用、分阶段执行、限制返工和减少重复输入；不能删除困难条件或只保留容易通过的案例。
6. **`keep` 只表示本版本通过已声明的有限测试。**不声称发现了所有缺陷，也不自动授予训练准入。

过滤单位：`task_id + data_hash + environment_hash + initial_state_hash + verifier_hash + judge_config_hash + protocol_version`。

### 贯穿示例

假设原题为“把商品A的价格改成80元，并告诉我修改后的价格”，初态价格为100元。分析LLM先提出两个结果条件：正确商品的末态价格为80，最终答复正确报告80；对象定位依据也要核实。执行LLM经公开工具找到A并修改，程序查询实际状态。

| 实际执行结果 | 经证据核实后的标签 | 官方Judge应给出的结果 |
|---|---|---|
| A变为80，答复80 | 正例 | 成功 |
| A变为80，答复使用另一种合法措辞 | 合法替代正例 | 成功 |
| A变为90，答复90 | 负例：价格要求未满足 | 有效不成功 |
| 改了B，A仍为100 | 负例：目标对象要求未满足 | 有效不成功 |
| A变为80，答复90 | 负例：明确答复要求未满足 | 有效不成功 |

此表是讲解示例，不是通用于全部题目的固定五例模板。题面、初态或工具契约变化时，应重新确定条件与覆盖；若某个改价工具不支持90或没有合法可访问的B，就不能假装相应反例已成功构造。

## 2. 与现有流程的关系

现有 `scripts/two_layer/prompts.py` 已经让模型逐题生成检查 SQL 和案例，并非遇到新题就只查固定规则库。主要变化是：

| 项目 | 本方案采用的做法 |
|---|---|
| 正例构造 | 通过真实工具交互逐步完成；允许循环、分页、从前序结果解析参数 |
| 执行表示 | 小段 Python 调用受控工具接口，或原生多轮工具调用；不受现有不支持 foreach 的 JSON 配方限制 |
| 顺序 | 先确认要求，再跑通并核实正例，然后构造反例 |
| 核查条件 | LLM 动态生成，但必须有原文依据、可执行核查和独立复核 |
| 复核输入 | 先看短证据索引和关键事实，缺什么定向取什么；不默认反复塞入整表和所有轨迹 |
| 修复 | 对具体失败项局部修复；规则变化时使受影响标签失效并重新核查 |
| 暂存 | 按工程、语义、标签、运行、预算分开，必须记录下一步动作 |
| Judge 验收 | 沿用每个正式案例 5 个固定判定槽位；不取多数票，不挑选最好结果 |

运行方式要先选定：可以由 Codex 会话组织这些工作，也可以由程序调用配置的模型 API；不要把同一阶段同时执行两套模型流程。程序模型请求记入 API 账本；Codex 会话、人工复核和本地计算的用量分别记录，无法取得的用量标为未知，不能记为零。

## 3. 分工、信息隔离与输入输出

下列是逻辑角色，不要求启动多个 Agent 或使用多个供应商；可以顺序运行。角色切换必须使用明确的输入白名单，不能仅靠同一会话里一句“忘记前文”。

| 角色 | 可以看到 | 不可以看到 | 交付 |
|---|---|---|---|
| 预期结果分析 LLM | 题面、公开工具契约、真实 schema、审计只读查询结果、已核实环境事实 | 官方 verifier 代码、官方判分、历史 keep/reject 结论 | 带来源的成功条件、检查代码候选、未决问题 |
| 正例执行 LLM | 题面、公开工具契约、实际工具返回 | 私有数据库快照、审计查询结果中的隐藏 ID、官方 verifier、私有标签和参考答案 | 真实完成轨迹与最终答复 |
| 案例构造 LLM | 已核实条件、正例的公开调用配方和响应、适用的覆盖义务 | 官方判分与 verifier 内部条件 | 正确变体、负例干预计划和可重放操作 |
| 独立复核 LLM | 完整题面、公开契约、真实数据库证据、检查代码、候选案例 | 在标签冻结前不看官方判分和 verifier 条件 | 条件核查、标签依据、覆盖缺口、具体问题 |
| 官方 Judge | 原版程序应收到的题面、真实轨迹、最终答复及官方 SQL 证据 | 私有成功条件、测试标签、复核意见 | 原始响应、有效性、成功/失败判定 |
| 分歧复核 LLM | 冻结标签与全部相关证据、实际官方请求和响应 | 无需隐藏本次分歧 | 标签错误、输入错误、Judge 错误或证据不足的归因 |
| 确定性程序 | 管理全部工件、权限与版本 | 不自行猜测题意 | 执行、快照、检查、计费、比较、状态汇总 |

案例构造者即使知道私有成功条件，也只能通过真实工具取得执行所需的动态对象 ID。工具执行层检查参数来源：题面字面量、公开常量、前序工具返回、登记的确定性计算。审计数据库中查到的隐藏 ID 不得直接注入执行轨迹。

拟议执行隔离：模型生成的检查代码在独立进程中读取只读数据库副本和只读轨迹；执行配方只获得自己的环境及公开工具接口。预算账本、官方结果、冻结标签及原始工件由程序写入，生成代码不能覆盖。模型API凭据只保存在请求调度层。限制进程时间和输出大小；禁止检查代码直接修改待检状态。代码语法校验不能替代这些运行权限边界。

## 4. 全流程与逐步验收

| 步骤 | LLM 做什么 | 程序做什么 | 产出／进入下一步的条件 |
|---|---|---|---|
| S0 冻结与预检 | 默认不调用；只在具体缺陷归因需要时使用 | 资产绑定、哈希、初始化、服务启动、schema、时间、重置与隔离检查 | `environment_facts.json`、`preflight.json`；环境可启动且绑定明确 |
| S1 生成预期结果 | 理解任务，按需查真实数据，提出条件和 SQL/Python 检查 | 提供受限只读查询，校验结构、引用、代码可执行性 | `requirements.candidate.json`、`checks.candidate.py/sql` |
| S2 独立核实要求 | 冷启动提取要求，再与候选条件比较；复核对象、范围、计算 | 保存盲审结果，再开放候选文件；运行独立证据查询 | `requirements.frozen.json`、`requirements_review.json`；无未解的实质条件争议 |
| S3 执行正例 | 从公开信息实际调用工具完成任务；必要时局部修正调用代码 | 新实例、真实 MCP、schema 检查、逐步状态与响应记录 | `positive_attempt/`；有完整轨迹和可检查终态 |
| S4 核实并重放正例 | 核对结果是否满足所有要求、依赖工具行为是否正确 | 执行检查；在另一份相同初态重放成功配方，核对语义结果 | `positive_verified.json`；至少一个正例有效，重置与重放成立 |
| S5 构造正反变体 | 基于正例选择最小有效干预和合法替代方式 | 先执行可确定的变体；需要交互时再调用模型；每例独立环境 | `case_candidates.jsonl`、真实案例工件 |
| S6 核实标签与覆盖 | 复核每个案例实际违反／满足的条件；检查未覆盖项 | 执行全部条件，生成覆盖矩阵、校验标签及工件哈希 | `frozen_cases.jsonl`、`coverage.json`；全部正式标签有依据 |
| S7 官方 Judge | 官方 LLM 按原提示词判定；仅出现分歧时启动额外归因 | 原版 SQL 取证、检查实际请求、固定槽位判定、保存 usage | `judge_results.jsonl`、必要时 `disagreement.json` |
| S8 汇总 | 默认不再调用模型写总结 | 按明确状态机生成台账、成本表、有限测试发布清单 | `keep/reject/quarantine`；每题可追溯 |

### S0：先排除运行前就能发现的问题

- 复用本地结构筛查，但必须匹配数据、源码、依赖、初态、工具契约及时间设置；不同版本不能直接继承通过结论。
- 原始初始化失败在第二个新实例复现。区分本机依赖、端口、超时与发布环境本身的缺陷。
- 单纯编译成功不证明工具业务正确。任务实际依赖的工具，在 S3—S6 用真实返回和 DB 核对。
- 全局初始化／重置缺陷可阻断整个环境；局部工具缺陷仅传播到确认依赖且无已验证合法替代路径的任务。
- 时间题记录真实时钟、时区及初态生成时点。若原生机制无法固定必要时间，不选择有利时点强行过检。
- 快照应由 SQLite 一致性备份获得，避免只复制主文件遗漏 WAL 中的状态。多重集差异保留重复记录，不能用集合去重后比较。

### S1—S2：生成的是“约束”，不是猜一份完整末态

任务要求“新建一个对象”时，新 ID 不必提前确定；检查新对象满足指定属性及关联关系即可。不同合法 ID、无要求的排列差异或措辞差异不能判错。

每个条件记录：

```json
{
  "id": "r_price",
  "kind": "required_outcome",
  "source": {"artifact": "task.txt", "quote": "把商品A的价格改成80元"},
  "target": "从公开查询结果解析到的商品A",
  "expectation": "最终价格为80",
  "evidence_inputs": ["initial_db", "final_db", "tool_results"],
  "check_ref": "checks.py::check_price",
  "normalization": "按公开字段类型比较价格",
  "unresolved": []
}
```

`kind` 区分 `required_outcome`、`required_answer`、`contract_precondition`、`context_fact`。已知当前用户、对象初始归属等事实，不自动成为每题必须额外构造反例的输出条件。

检查函数建议返回：`pass | fail | unknown | error`，并附查询、参与记录、实际值、期望条件和证据引用。SQL 返回空集合究竟是正确答案还是缺证据，必须由题目条件决定；不能通用地把空结果当失败。SQL/Python 能运行，仅证明可执行，不证明语义正确。

独立复核采用两次受控输入：

1. 先只给原题、公开契约、schema 和查证接口，保存独立要求清单与关键事实。
2. 再给候选条件及检查代码，逐项核对遗漏、无依据限制、对象、时点、集合范围和计算。

不强制生成第二套完整可执行检查代码。范围和聚合必须保存可复算记录；复核者要检查记录选择依据，不能只再运行同一条可能错误的 SQL。

例：“最近30天”与“本月”必须区分；“我的主门店”若已有公开身份和默认门店接口能唯一解析，就不是歧义。真正的歧义应列出两种均有依据的解释、各自产生的不同结果，以及已经查过仍不能消解的来源。

### S3—S4：真实执行正例，先完成一条闭环

LLM 可以使用多轮工具交互，或编写 Python 调用受控的 `list_tools/call_tool` 接口，支持 `for`、分页及结果解析。实际接口以实现时定义为准；本方案未新增可调用 SDK。

- 写操作只能通过 MCP，不能直接写数据库来制造“成功轨迹”。
- LLM 只看到执行角色允许的公开信息。核查程序在角色外读取初末数据库。
- 每个工具调用核对公开契约涉及的读写行为：对象、过滤范围、返回字段、真实写入及声明的副作用。
- 先让一个候选正例满足全部结果要求，再在第二份相同初态执行配方。重放动态重新解析 ID，不能直接复用首次新增记录的 ID。
- 对允许的随机 ID／时间字段比较有依据的语义结果；不要求整个数据库字节相同。必要结果本身不可重现时保留运行问题。
- 工具报错、模型不会做、步数不够、脚本能力缺失都不是任务无解的证据。
- 正例没通过时，不提前生成完整负例集合。只修具体失败项，或转入明确的缺陷／待补状态。

### S5—S6：反例是候选，执行后才能定标签

覆盖义务在调用 Judge 前固定：

| 风险 | 案例要求 |
|---|---|
| 基本可完成性 | 一个经过真实执行、全部条件满足的正例 |
| 过度严格 | 至少一个可构造的合法替代正例；确无适用变体时给出具体依据并复核 |
| 错对象 | 修改／查询另一个真实可达的对象；不能编造不存在的 ID |
| 错值、漏要求、漏操作 | 每项可独立违反的结果要求都有相应负例；允许有证据的联合覆盖 |
| 批量和集合 | 根据题目检查遗漏、多出、错误成员；不凭空添加题目没有的排他限制 |
| 时间与计算 | 核查适用的范围、边界、时区、聚合成员及数值 |
| 明确输出要求 | 错误值、缺少必要内容等；只读题不能只看数据库未变化 |
| 无操作、重复与副作用 | 仅当实际违反明确要求或公开契约时，才能贴负例标签 |

每条覆盖义务只能为 `covered`、`not_applicable_with_evidence`、`missing`。`missing` 不许以“预算小”“例子够多”变成通过。

具体执行：

1. LLM 一次提出干预计划，列出想违反的条件及原因。
2. 程序优先重放已成功配方并替换参数、删除某一步或替换最终答复；如改动会影响后续引用，重新解析依赖，不能产生虚假轨迹。
3. 无法通过已有配方表达时，再由案例执行 LLM 在新实例中完成干预，计入单独预算。
4. 所有案例重新运行全部检查。正例需全部明确满足；负例至少一项明确违反，并记录其他受影响条件。
5. 如果案例结果未满足生成者的意图，记为 `case_build_failed`，修构造；不能假定原标签仍成立。
6. 纯答复变体可以共享同一次真实读取证据，但必须标为测试变体，并在官方原生轨迹中替换实际被测试的最终答复；不更改工具返回。
7. 直接改数据库的状态仅作隔离诊断，不冒充工具可达案例；未经可达性验证，不据此认定正常执行中的误判。

缺少事实的检查必须返回 `unknown`，不能因程序未抛异常而当作 `pass`。合法替代正例必须满足完整要求，不能只做表面改写。

### S7：官方 Judge 接收真实事实，程序比较已核实标签

先完成两项离线检查：

- 运行官方 SQL 取证，记录执行异常及实际输出；SQL 取证程序默认的状态字段不是最终 LLM 判分。
- 在发送边界核对实际请求中的题面、工具调用／响应、最终答复和 SQL 结果。若正反例对 Judge 的完整可观察输入相同，却要求不同标签，先检查输入缺失和标签问题，不发送重复请求掩盖问题。

正式调用沿用冻结官方配置。当前本地源码 `run_llm_judge` 使用 `temperature=1.0`、`max_completion_tokens=4096`；实施时重新冻结确认。不能为了降低成本私改官方提示词、裁剪官方证据或降低其输出上限，仍声称原配置已通过。

每个正式案例安排 5 个槽位：

- 正例预期有效 `complete`。
- 负例预期有效的不成功判定；`agent_error` 只有与案例事实相符才算识别成功。`server_error`、`judge_error`、截断、解析失败都不算有效拒绝。
- 先对各案例运行槽位0，再运行后续槽位，优先暴露明显缺陷。仅在全部应有槽位有效且符合标签时，该案例通过。
- 每个有效错误判定都保留。不能重采样直到凑够5次正确，也不取多数票。
- 先发现一个分歧，就暂停该题后续付费槽位并归因；确认官方 Judge 缺陷后可提前 `reject`，不必消耗剩余槽位。
- 传输失败初版默认不自动重试；恢复采用明确记录的槽位策略和累计预算。已发出但没有 usage 的请求保留保守预留。

比较逻辑：

| 核实标签 | 官方有效结果 | 处理 |
|---|---|---|
| 正例 | 成功 | 本次槽位符合预期 |
| 负例 | 不成功且归因符合事实 | 本次槽位符合预期 |
| 正例 | 不成功 | 误拒疑点；复查标签、输入和取证 |
| 负例 | 成功 | 误放疑点；复查标签、输入和取证 |
| 任意 | 无效／异常／未返回 | 运行未完成，不作语义结论 |

分歧后允许修复错误的测试条件，但必须有原文或事实证据并创建新版本；旧标签和判定完整保留，受影响案例重新生成／核实。不得以“与官方一致”为修标签的理由。

### S8：发布状态

`keep` 必须同时满足：题意已核实、任务依赖范围内环境工具通过、正例及重放成立、所有正式标签核实、适用覆盖完成、官方输入正确、每例5个槽位全部有效且符合标签、无未解决的实质分歧。

`reject` 必须有复现或充分证据支持当前版本组合的硬缺陷。原因分开保存：`environment_defect`、`task_contract_defect`、`judge_defect`；Judge 缺陷不意味着题目本身无价值。

其余统一属于 `quarantine`，但必须细分原因。`keep` 发布包与私有条件、测试标签和参考配方分离；本阶段不启动训练。

## 6. 暂存如何变成可处理事项

| `quarantine_reason` | 典型情况 | 下一步 | 绝不能据此做的事 |
|---|---|---|---|
| `engineering` | SQL列名错、循环未支持、参数解析错误 | 局部修实现，重跑受影响步骤 | 判坏题或改变题意 |
| `evidence_missing` | 对象归属／工具返回／必要记录未取得 | 一次定向查证；仍缺则列具体缺口 | 编造默认值 |
| `semantic` | 两种有依据的解释产生不同结果 | 按任务族集中复核必要契约 | 反复换模型直到有人同意 |
| `label_disputed` | 正例漏要求、反例不一定错 | 修条件或案例并创建新版本 | 以官方判分反推真值 |
| `binding` | 同任务对应不同 verifier | 核对原资产与版本 | 随便选一个有利版本 |
| `runtime` | 超时、模型截断、API错误 | 保存断点，按恢复策略处理 | 作为有效负例或误判 |
| `budget` | 不够完成剩余案例／槽位 | 记录已花费、剩余工作与估算 | 少测几个就宣布通过 |

每条暂存必须包含：`blocked_stage, root_cause, evidence_refs, attempted_fix, next_action, estimated_remaining_calls, protocol_version`。

一题可同时有多个原因；另设首要阻塞项便于排队。不能因存在某个 `ambiguities` 字符串，覆盖已确认的工程错误并直接结束。`unresolved` 是诚实的结果，但应回答“具体哪一步缺什么”，而不是泛泛写“需人工检查”。

修复默认最多每题2轮，且每轮只能针对有证据的具体问题。每轮没有取得新事实或修复新错误就停止；预算是停止自动尝试的依据，不是改变题目质量标签的依据。

## 7. 成本控制

### 7.1 已有成本作为基线

原100题两层清洗的账本已报告 10,871,304 tokens（不含70-token连通检查和13次未返回usage的请求）：

| 阶段 | 已报告 tokens | 占已报告总量 |
|---|---:|---:|
| 构造及修复 | 2,792,243 | 25.68% |
| 独立提取及修复 | 1,913,440 | 17.60% |
| 复核 | 4,621,096 | 42.51% |
| 官方 Judge | 1,536,924 | 14.14% |
| 分歧复核 | 7,601 | 0.07% |

这是一批未全部完成认证的任务的总消耗，不能直接作为“每道成功认证题”的未来单价。也不是金额占比；缓存、输入和输出价格不同，账本没有可靠货币成本。

### 7.2 优先减少重复工作

1. 同版本环境事实、工具发现、schema和基础检查复用；任务语义及参数分支仍逐题检查。
2. 程序先执行schema、来源引用、SQL语法等机械校验，再请LLM看语义；不能让模型反复承担能确定的语法检查。
3. 正例先核实，反例后展开。失败正例不触发完整负例构造和官方判分。
4. 单次规划多个反例，由程序重放执行；不默认每条反例都启动完整模型解题。
5. 独立要求复核不默认再生成一整套检查代码；保留独立阅读原题和关键事实核查。
6. 复核先给证据索引、条件结果、关键行和差异；分页取证按需补充。聚合需要完整参与集合或可复算查询，摘要截断必须显式标明，不能隐藏缺失。
7. 已核实工件按数据、时间、代码、条件、配方与模型配置哈希缓存。修改上游工件使受影响标签与结果失效；预算账本保留全部旧成本。
8. Judge 不提前派发。相同版本正式案例的已完成槽位断点复用；重复读取同一结果不当作额外独立槽位。
9. 每题出现确证缺陷即停后续付费步骤。已经通过的正例若无版本变化，不因另一题失败而重复执行。
10. 记录每阶段实际输入、输出、缓存用量及工具调用；不能靠并行提高速度后声称节省tokens。

### 7.3 模型请求与工具调用分开预算

一次 LLM 回合可能调用多个工具；每次把工具结果发回模型继续推理，都是新的模型调用。Python循环重放100次本地工具，不必等同100次模型请求；本地计算和存储仍有成本。

建议初版工作限额，均为**待实施时校准的设计上限，不是已经批准的运行预算**：

| 项目 | 建议上限 | 到限后的处理 |
|---|---:|---|
| 单题正式案例数 | 8 | 覆盖未满则转复杂题队列，不删覆盖义务 |
| 单例官方Judge槽位 | 5 | 保持现有严格协议 |
| 正例交互模型回合 | 6 | 工具步数与回合分别计数；不足转待补 |
| 案例构造额外交互回合 | 每题合计4 | 优先程序变体；不足转待补 |
| 独立复核补充证据回合 | 每题合计2 | 必须指明要补的事实 |
| 局部修复轮数 | 每题2 | 不无限循环 |
| 单题全部物理模型请求 | 64，含Judge及失败请求 | 达到任一上限即停止派发 |
| 单题累计token占用 | 200,000 | 含已报用量和未结束请求预留 |
| 非Judge单次实际输入 | 16,000 tokens | 先缩小到相关证据或分页；仍不够转复杂题队列 |
| 非Judge单次输出 | 一般2,000；写检查代码最多4,000 tokens | 截断不能按完整结果继续；重试计入修复预算 |
| 官方Judge输入／输出 | 保留原始内容和冻结配置 | 太大则标预算或上下文阻断，不偷偷截断 |
| 自动传输重试 | 0 | 保存失败，恢复必须可追溯且受总预算约束 |

这些上限对复杂多步题可能不够；报告复杂题比例和原因，不能用提高通过率的方式隐藏选择偏差。每个上限单独生效，不能因为总预算尚有余额就自动突破单题上限。

### 7.4 默认关闭与拟议小样本预算

```yaml
# 设计示例，本文没有创建实际运行配置
execution_enabled: false
model_calls_enabled: false
authorization_scope: none
max_total_tokens: 0
max_physical_requests: 0

# 若后续明确批准试跑，才讨论启用以下独立配置；此处不是授权
proposed_pilot:
  task_count: 5
  max_total_tokens: 1000000
  max_physical_requests: 320
  max_tokens_per_task: 200000
  max_requests_per_task: 64
  max_concurrent_requests: 1
  judge_slots_per_case: 5
  max_formal_cases_per_task: 8
```

环境级模型调用也计入总额，所以并不保证5题各自都能耗满单题额度。执行前冻结任务ID和范围；旧运行的授权不自动转入本新协议。5题只校准工程与预算，不用于推断全库质量。

调度器必须在请求发送前原子预留：

`本次预留 = 实际完整请求的输入token保守上界 + 本次最大可计费输出token`。

输入计算包括system、历史、工具schema和工具结果；尽可能使用匹配的tokenizer，不能把字符数直接当token数。无法取得可靠上界时停止自动派发并校准，不用偏小估算绕过预算。收到usage后对账；usage缺失或是否送达不明时保持预留，重复请求照样累计。金额限制只有在单价与缓存规则核实后才能可靠启用。

在进入Judge阶段前，根据全部正式案例数、5槽位和当前请求长度估算剩余费用；预算明显不够时先保留预检结果，避免把大量题做到半途。估算不替代逐次预留。

### 7.5 一道题的算术示例，非实测报价

假设一题需要10次非Judge调用（含工具交互），平均每次2,500输入+800输出；有6个正式案例，每例5次Judge，每次3,500输入+700输出：

- 非Judge：`10 × 3,300 = 33,000 tokens`。
- Judge：`6 × 5 × 4,200 = 126,000 tokens`。
- 合计：`159,000 tokens/题`，不含未知用量和其他额外调用。

这只是展示变量关系，不能据此声称新方案便宜。旧流程主要耗在构造复核；新流程若更多题进入完整Judge验收，Judge可能成为主要成本。输入变长、反例变多或交互回合增多都会增加费用。

试跑后分别报告：全部尝试成本、每阶段成本、每个得到明确结论任务的成本、每个keep任务的成本、剩余工作成本估算。分母为0时写未定义，不造平均数。不要把未完成题算成廉价完成。

## 8. 小样本验证与停止条件

后续实施分两步，本次均不运行：

1. **工程校准5题**：从旧原100题选取简单写入、明确只读输出、批量任务、已确认工具缺陷和已确认Judge缺陷。模型审计时隐藏历史最终结论；评估者持有冻结证据检查归因是否正确。
2. **冻结协议后的验证样本**：再选择未用于修改prompt和执行器的题，跨环境及读写类型，并在预算核准后运行。若为20题，应明确只是小样本适用性观察；条件不足或模型失败的题不能换成容易题。

扩大前检查：

- 真实工具执行和快照能重放；提示词信息隔离有效。
- 已知硬缺陷能定位到事实，不只重复旧结论。
- 未发现把合法替代答案误判为负例的未解决问题；检查覆盖仍有缺口时不放行。
- 工程错误能归入修复队列，不被“语义歧义”覆盖。
- 每个keep案例均有完整条件、标签证据及5槽位记录。
- 预算累计与供应商usage相符；未知用量独立计入预留。
- 与旧记录比较同一任务、可比测试范围的成本和完成情况；不能把不同样本或不同严格度的百分比当成提升。

如果模型持续添加题面没有的条件、案例标签无法独立核实、或复核成本仍占主要部分，先停止扩量并调整证据供给和具体prompt。没有预设最低keep比例，不能为了达到数量目标降低要求。
