# 接手后的清洗策略

> 2026-10-23 范围更新：当前清洗按[两层清洗方案](two_layer_cleaning_plan_zh.md)执行设计：第一层为环境、数据库和工具；第二层为答案及官方 SQL+LLM Judge 的可靠性。下文保留为旧策略与历史筛查说明，其中轨迹、SFT、GRPO 准入讨论不属于本阶段范围。新文档目前仅为设计稿，未执行新一轮清洗。

原流程做的是逐题完整认证：每道题要有独立规则、成功重放、完整反例、工具业务检查、SQL 取证复核和多次 Judge 结果。旧实现只有一道题完成完整插件，所以 0 keep 不能作为其余题都不合格的证据。

这次改成缺陷筛除。例子：一道题要求修改车辆价格，工具和数据库都正常，但没有人为写好的独立规则，题目继续保留；如果同一份原始 SQL 在两个全新数据库都报语法错误，则排除当前环境实例，并保存 SQL、错误和数据库。被排除的是坏环境版本下的实例，修复环境后仍可重新评估题目。

必须分开三件事：

1. **任务/环境有没有明确缺陷**：坏初始化、原始代码无法编译等可复现错误。
2. **某条答案/轨迹是否正确**：直接核对题面明确要求、工具返回、初末状态与最终答复；单次 Agent 失败不证明题目错误。
3. **判分器是否可靠**：SQL 绑定冲突、取证范围错误、Judge 忽略答案等。判分器出错可以保留题目，停用对应奖励配置。

本轮脚本自动完成第一层的结构/初始化筛查、第二层的旧证据整理以及第三层的绑定检查；没有完成全库逐题语义验证。`retain` 意味着保留候选，不意味着答案正确。当前所有记录 `training_ready=false`，避免接手时误把结构清洗结果当成已经语义认证的训练数据。

## 为什么不能直接相信 96.4%

旧报告从本地原始 cases 重算：SQL+LLM 在 224 个有效构造案例中与旧规则一致 216 个，正例通过 43/48，负例误放 3/176。27 个截断输出和 8 个资产错误排除在分母外。样本正负比例由构造方式决定，标签也来自需要复核的规则。这既不是全库正确率，也不是 100 道题的答案正确率。

本轮追查 8 个分歧发现既有 Judge 问题，也有旧规则漏检与时钟/范围约定问题。见 `evidence/disagreements/review_zh.md`，不能把 8 个分歧全部直接叫作模型误判。

## 后续语义清洗应怎么做

采用“证据先行、只升级异常”的方案：

- 从题面提取明确要求，并逐条保留原文依据。未指定唯一一条、固定工具路径或固定措辞时，不自行增加条件。
- SQL 负责给出真实对象、字段、数量、初末差异，LLM 判断这些证据是否满足要求。只读题必须同时检查最终答复；写操作必须核对实际状态，不能只信“已完成”。
- 正常案例做一次初筛，存在矛盾时才交叉核查。可以让另一轮审查者先看题面和证据、独立判断，再看原规则/Judge；多数票不是事实真值。
- 优先验证当前已发现的争议，以及错对象、漏关键要求、返回空答案、错误数值等明确反例。反例违反哪条要求必须能指向题面或公开工具契约。
- 对通过候选按环境、读写任务、时间依赖和复杂度分层随机抽查，冻结抽样 ID 与版本；单列无效输出、工具失败、标签争议。再决定是否扩大付费解题/判分。
- 把“任务是否删除”“轨迹是否可用于 SFT”“verifier 是否可用于 GRPO 奖励”作为三个字段维护。不能因某条轨迹错就删题，也不能因题目保留就自动允许奖励。

这能减少逐题写死规则的工程量，但不能省掉明确问题的证据复核。对于未检查的语义，不声称已洗干净。
